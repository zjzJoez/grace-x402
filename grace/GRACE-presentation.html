On the merchant side, agent orders are indistinguishable from legitimate orders. There is no chargeback reason code for “my agent did it,” so a rational merchant must reject the traffic or price in the risk.

On the buyer side, on-chain payments are instantly final. A rational person will not hand real money to an agent with no chance to intervene.

Existing answers share the same premise: first take custody of the money, then discuss whether it can be returned. GRACE changes that premise.

StraitsX AgentiX Playground 2026 · Track 3 — AI-native Commerce 03 / 06

XSGD is a Circle-standard token contract with EIP-3009 authorization transfers. Every authorization already contains validAfter: the time when the signature becomes usable. Production integrations normally put that time in the past. GRACE puts it 90 seconds into the future.

Inside that window, the merchant holds a signed and amount-locked claim, but the chain refuses to cash it. The buyer keeps a unilateral veto. A phone with zero AVAX can sign the cancellation, while any relayer pays the gas.

Neither side can exercise the other side’s power. No third party can exercise either. Nothing was escrowed, so reversal costs nothing because nothing moved.

How one payment lives.

03Settle. EventBridge wakes Lambda; the token decides.
StraitsX AgentiX Playground 2026 · Track 3 — AI-native Commerce 04 / 06

A payment has three steps. Before signing, Claude on Bedrock performs an advisory purchase check. The guarantee is not the model; the guarantee is the window, because GRACE assumes agents will sometimes be wrong.

During the window, the buyer can veto. When validAfter arrives, EventBridge Scheduler wakes a Lambda and asks the merchant to settle. The cloud can only ask. The XSGD contract decides whether settlement is valid.

The trust boundary is explicit: the payee key lives with the merchant, where it already must. The scheduling layer has no keys. At-least-once delivery is safe because the nonce makes settlement idempotent: a duplicate attempt simply reverts as already used.

At the protocol layer, exact-deferred is a backward-compatible x402 scheme extension. The merchant declares the window per SKU; zero seconds becomes today’s exact flow. The mechanism works with any EIP-3009 token, including USDC.

Most of the category is solving how to make agents pay. GRACE solves the other half: how to make merchants willing to accept agent money.

The honest boundary is intent finality, not solvency. The buyer could move funds during the window, so the merchant flow is settle, then ship. A failed settlement is a lost sale, never a lost good.

For StraitsX, the dispute-protection layer already lives inside the token standard it has deployed. exact-deferred can be documented without deploying a new contract.
