# Settlement status: draft state table for review

**Scope.** This amends `SettleResponse` (§5.3.2) with three OPTIONAL fields and adds two subsections, §5.3.3 and §5.3.4. §5.3.5 below is normative in each binding's own scheme specification, not in the core spec. It does **not** touch `VerifyResponse` (§5.4.2): permitting a future `validAfter` to *survive* verification instead of being rejected is a change to verifier behaviour, it belongs to #3182, and it is deliberately out of scope here so that nobody reads its absence as an oversight. Absence of `status` keeps today's exact v2 semantics — vocabulary only, no flow semantics, which is the property @glennquinting praised on 20 Aug and the property I most want to keep.

**Why core and not `extensions/`.** §5.3.2 already has an `extensions` object and `specs/CONTRIBUTING.md` scopes `extensions/` to "optional functionality beyond core payment mechanics", so the lighter shape is available and I am not taking it. The reason is uniform adoption: a reader like merona's index has to interpret every facilitator's settlement, and a status vocabulary that only some responses can legally carry is one an index must treat as absent by default — which is the evidence-free bucket again, one layer up. If the group prefers `extensions/`, that is a real option and I would rather argue it in review than have it assumed.

**Deliberately small.** #3083 — the only merged precedent for adding a settlement state — was 80 files, +4418/−668 overall; its `specs/` slice was +11/−1 across four files, of which the core spec was +2/−1. This is spec-only, two files (`specs/x402-specification-v2.md`, `specs/schemes/exact/scheme_exact_evm.md`), and roughly +90 core-spec lines — heavier than #3083 in the core spec and lighter in file count. SDK parity, if wanted, follows in separate PRs. The previous version of this draft declared 20+ bindings and would have touched most of the 26 files under `specs/schemes/`, pulling in every network team as a required reviewer. Three capability rows here; every other binding declares in its own scheme spec, in its own PR, reviewed by the team that owns it.

## The three rules

**R1 — anchor per state.** @peppe1337: "a vocabulary only helps if each non-terminal state is *required* to name its anchor … Otherwise the practical effect is one evidence-free bucket becoming four." The phrasing @glennquinting asked to survive into the rationale is @jywy78kgrf-create's, not mine: "a state names an on-chain object a stranger can check, or it names that it has none."

**R2 — the capability declaration names its enforcement object.** @glennquinting established that `deferred_until(T, basis: enforced)` is inexpressible on Nano; @jywy78kgrf-create refined the remedy — it "has to **name the verifiable enforcement object, because that object is the anchor**."

**R3 — malformed, not downgraded.** @glennquinting's option (a): a reader encountering `deferred_until` on a binding that has not declared the capability treats it as malformed. His option (b) is not withdrawn, only not chosen.

## §5.3.2 — three new fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `status` | `string` | Optional | One of the six literals `settled`, `pending`, `deferred_until`, `blocked`, `canceled`, `expired`. When omitted, this section does not apply and the response carries today's v2 semantics unchanged. |
| `statusAnchor` | `object` | Optional | REQUIRED when `status` is present. The evidence object; shape in §5.3.4. |
| `statusDetail` | `object` | Optional | REQUIRED when §5.3.4's parameter list gives the state parameters. |

The parameterised notations `deferred_until(T, basis)` and `canceled(by)` are prose shorthand for the wire string plus its `statusDetail` members; they are not values.

**Which settle.** `status` is defined for the **collect** settle — the one that records the final charge (`authorization`, `upfront`, and the second settle of `escrow`). §7.2 permits `/settle` to be invoked more than once for one payment, and `auth-capture` returns a `SettleResponse` from `authorize`, `capture`, `void`, `refund` and `reclaim`. Facilitators MUST omit `status` on those lifecycle settles. A state for "committed something, not the final charge" is a real gap and is out of scope here.

**What `success` and `errorReason` carry.** `success` is Required and boolean, so the table has to say what it is for every state.

- `settled` → `success: true`, `errorReason` omitted.
- `pending` → `success: false`, `errorReason: settlement_pending`, non-empty `transaction`. This is that code's alias for the broadcast-confirmation-unknown case only. Where the anchor is confirmed but not yet final by the binding's rule, `pending` is emitted with `errorReason` omitted; this amendment does **not** widen §9's `settlement_pending`, whose gloss stays as merged.
- `blocked`, `deferred_until`, `expired` → `success: false`, and each MAY carry the existing §9 code for the same fact: `insufficient_funds` for `blocked`, and on `exact`/eip3009 `invalid_exact_evm_payload_authorization_valid_after` and `..._valid_before` for the other two. Those last two are settle-side codes the reference facilitator already returns today (`eip3009.ts:518` → `parseEip3009TransferError`, `eip3009-utils.ts:279-285`), so requiring `errorReason` omitted here — as the previous draft did, on the false ground that §9 has no code for these — would have told an implementer to stop emitting a code the reference implementation emits. Terminality comes from `status`, never from the code.
- `canceled` → `success: false`, `errorReason` omitted. `canceled` is the one state §9 genuinely has no code for, and a facilitator MUST NOT substitute the mechanism-level `invalid_exact_evm_nonce_already_used` (`errors.ts:28`), which asserts the opposite fact.

**Compatibility.** A response that omits `status` carries no status information: this amendment says nothing normative about how to read it, which is what "absence keeps today's semantics" has to mean. Where a §9 code accompanies a `status`, terminality comes from the `status`; a reader MUST NOT infer terminality from `insufficient_funds` or from `invalid_exact_evm_payload_authorization_valid_after`, which record what the emitting facilitator could express rather than a fact about the authorization. Every §9 code except `settlement_pending` — which §9 itself marks **non-terminal** — remains terminal when it appears alone, as an `errorReason`. Readers MUST treat an unknown `status` value as unsupported rather than mapping it to the nearest known state.

## §5.3.3 — the six states

`Subject` is what the state is terminal *about*. It is the fix for a defect in the previous draft, which defined terminality over the authorization while several states are terminal only for an attempt.

| `status` | Subject | Terminal | REQUIRED anchor | A reader MUST NOT conclude |
| --- | --- | --- | --- | --- |
| `settled` | authorization | Yes | `kind: "event"`, `"transaction"` or `"composite"` — the scheme-defined settlement object; plus `ledgerTime` where the binding declares a consensus time source | that the settlement matched the intent beyond the fields the anchor commits to. Value moved; *which* purchase it discharges is scheme-defined |
| `pending` | attempt | No | `kind: "transaction"` — the broadcast reference, non-empty per §5.3.2. Post-broadcast only | that the transaction will confirm, or that it will not; and — from `pending` alone — that no receipt exists. Read `finality` |
| `deferred_until` | observation | No | `kind: "predicate"`, naming the declared enforcement object. `statusDetail.basis` MUST be `enforced` | that the payer will not settle later by another route, or — over a binding whose declaration is not `enforced` — anything at all |
| `blocked` | observation | No | `kind: "read"`, or `"composite"` where the binding's ordering coordinate is a separate part | that the condition persists past `observedAt`, or that it will clear. A mutable read is true only at the point it names |
| `canceled` | authorization | Yes | `kind: "event"`, or `"composite"` where the binding requires ordering evidence alongside the revocation artifact — on `exact`/permit2 it does. `statusDetail.by` names the party | cancellation from a consumed nonce, an invalidated bitmap bit, or a bumped sequence. Those prove unexecutability, not intent |
| `expired` | authorization | Yes | `kind: "none"`, `absentReason` stating the binding's expiry rule | that the payer refused, or that the authorization was ever presented. Expiry is silence and is indistinguishable from both |

**Terminality.** A terminal state MUST NOT be followed by a different status **with the same subject**. An attempt- or observation-scoped state never closes the authorization.

**Failure to resolve.** Where a reader cannot establish which state holds — a null read, a throw, an anchor that cannot be ordered, a claim the declaration does not cover — it MUST omit `status` entirely and fall back to `success`/`errorReason` per §9. It MUST NOT emit any of the six. This is @whawk46's rule from #3226: "When two opposite verdicts sit behind one flag, failing to resolve which cannot fall toward either — least of all toward the one that says money moved." The six states have no value for that case; see the deferred list below, which is the largest open item in this draft.

**Finality.** `settled` and `canceled` are terminal *with respect to the binding's own finality rule*, which the binding MUST name. A settlement observed at head can reorg. A facilitator MUST NOT emit a terminal status for an anchor observed at a depth the binding does not treat as irreversible; before that depth it emits `pending`, which therefore covers both "broadcast, confirmation not established" and "confirmed, not yet final". Those are different facts for an accounting consumer, so `statusAnchor.finality` discriminates them on the wire rather than leaving the reader to guess. That second half is where @cv-scvd's `PENDING_FINALITY` goes, and it is named rather than dropped.

## §5.3.4 — the anchor object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `about` | `object` | Required | The scheme-defined identity of the authorization this status describes, present on every status object regardless of `kind`. The binding MUST name its members — `exact`/eip3009 `{authorizer, nonce}`, `exact`/permit2 `{owner, nonce}`. A status object with no resolvable `about` MUST be treated as malformed |
| `kind` | `string` | Required | `transaction` \| `event` \| `read` \| `predicate` \| `composite` \| `none` |
| `network` | `string` | Optional | CAIP-2. REQUIRED when `kind != "none"` |
| `ref` | `string` | Optional | The scheme-defined reference the anchor lives in. Bindings MUST define its shape and MUST NOT assume a content hash |
| `locator` | `object` | Optional | Scheme-defined narrowing inside `ref`. The binding MUST name its members |
| `observation` | `object` | Optional | REQUIRED when `kind = "read"`. The contract or account read, the key, the returned values, and the binding's ordering coordinate where it declares one. The binding MUST name its members |
| `parts` | `array` | Optional | REQUIRED when `kind = "composite"`. Two or more anchor objects. ALL parts MUST resolve for the state to hold, and the binding MUST state the join rule relating them |
| `observedAt` | `string` | Optional | RFC 3339 UTC. REQUIRED on every non-terminal state |
| `ledgerTime` | `string` | Optional | RFC 3339 UTC, derived from the named object by a consensus rule the binding names. REQUIRED on `settled` where the binding declares a consensus time source; MUST be absent otherwise. A node-reported or facilitator wall-clock value MUST NOT be emitted in this field under any circumstances |
| `finality` | `string` | Optional | REQUIRED on `pending` and on terminal states. The binding-defined basis on which the anchor is treated as irreversible (`finalized`, `confirmations:<n>`, `slot-finalized`, or a binding-defined token), and on `pending`, `unconfirmed` where no receipt has been observed |
| `absentReason` | `string` | Required | A non-empty line stating why no anchor exists when `kind` is `none`; explicit `null` otherwise. R1 is machine-checkable as exactly this biconditional |

`composite` exists because several anchors are irreducibly a conjunction and the previous draft's single-object shape could not carry them. On `exact`/eip3009 the `settled` anchor is `AuthorizationUsed(address indexed authorizer, bytes32 indexed nonce)` — topic0 `0x98de5035…10a5`, both arguments indexed — **joined to** an ERC-20 `Transfer` in the same transaction whose `from` equals `authorizer`. One topic filter resolves the event; it does not resolve the join. A transaction MAY contain more than one qualifying `Transfer` — 36 of 2,526 in @jywy78kgrf-create's measured window did — so the join is per-`(transaction, authorizer)`, and the half that does the attribution is the half the wire format previously dropped. `canceled` and `blocked` take the same shape wherever ordering evidence or an ordering coordinate is a separate part.

`ledgerTime` was REQUIRED on `settled` in the previous draft, and @glennquinting's own rail cannot satisfy it: Nano state blocks carry no temporal field and `local_timestamp` is node-local metadata, not consensus data. Requiring it would have created pressure to pass a non-consensus number off under a consensus field name — R3 laundering arriving through a mandatory field, in the one column built to prevent it. Hence the declared time source. This addresses #3085 on bindings that have one; it does not close it rail-neutrally, and saying "closes #3085" was overclaiming.

**`statusDetail` members** — this list is the normative source the §5.3.2 row points at. `deferred_until` → `t` (in the declared unit) and `basis`; `canceled` → `by`. No other state takes parameters.

## §5.3.5 — the capability declaration

Normative in the binding's own scheme specification, keyed by rail × scheme × leg, not a wire field — because, as @jywy78kgrf-create put it, an index reading settlement data cannot tell `enforced` from `scheduled`: it sees the capture `Transfer`, never the predicate that refused earlier. Members: `capability` (`enforced` | `absent`), `enforcer`, `enforcerBinding` (`fixed` | `request-derived`), `field`, `comparator`, `unit`, `failureSignal`, `reason` (required when not `enforced`). `enforcer`, `enforcerBinding`, `field`, `comparator`, `unit` and `failureSignal` MUST all be explicit `null` when `capability` is `absent`, and `reason` MUST be present. Two further members are reserved now and left unpopulated: `version` (monotonic per binding) and `effectiveFrom` (CAIP-2 network plus the height at which the named object became the one in force), OPTIONAL today and REQUIRED once a binding's declaration changes its `enforcer`, `field` or `comparator` — a reader validating a historical settlement uses the entry in force at that settlement's height. That is @jywy78kgrf-create's answer to my own question, reserved in the shape without building a registry. A reader that encounters `basis: "enforced"` from a binding whose declaration is not `enforced`, or whose `enforcer`/`field` do not match it, MUST treat the status object as malformed, MUST NOT read it as a weaker claim, and falls back to the response's `success`/`errorReason` — i.e. today's semantics.

Two normative rows, plus one out-of-tree illustration that is **not** proposed as core-spec text:

| Binding | `capability` | enforcer · field · comparator · unit · failureSignal |
| --- | --- | --- |
| `exact` / eip3009 (EVM) | `enforced` | `request-derived`: the token named by `PaymentRequirements.asset`, which MUST implement EIP-3009 `transferWithAuthorization` and MUST reject `block.timestamp <= authorization.validAfter` · `authorization.validAfter` · `>` · unix-seconds · the observed signal on Circle's FiatTokenV2 is the reason string `FiatTokenV2: authorization is not yet valid`; other conformant assets MAY signal differently |
| `exact` / permit2 (EVM) | `enforced` | `fixed`: `x402ExactPermit2Proxy` at `0x402085c248EeA27D92E8b30b2C58ed07f9E20001` · `witness.validAfter` · `>=` · unix-seconds · `PaymentTooEarly()` / `0xa65539fa`, on **both** settlement entry points (`settle` `0x13cd3b53`, `settleWithPermit` `0xfa340378`) |
| *(illustration, out of tree)* Nano / XNO | `absent` | all enforcement members `null`. @glennquinting's own words, unedited: "capability absent, no enforcement object exists to name (state blocks carry no temporal field, and node-reported timestamps are non-consensus, so T can neither be enforced before broadcast nor audited after)" |

A facilitator MUST NOT emit `basis: "enforced"` for a request-derived asset it has not confirmed satisfies the stated predicate, and a reader MUST validate against the predicate, not the revert string. That is what makes `request-derived` checkable without naming a fixed address: another token exposing `transferWithAuthorization` may use `>=`, may revert differently, or may not gate `validAfter` at all, and a bare `enforced: true` would give a validator nothing to hold it to. Note also that the two live EVM enforcement objects **disagree by one second at the boundary** — EIP-3009 is strict, the Permit2 witness is inclusive — so a cross-rail reader validating a declared `enforced` against the chain gets a false mismatch at exactly `T` unless the comparator travels with the declaration.

A third capability value is needed for bindings whose rail can enforce a lower bound but whose x402 binding rejects one at verify. That case is real and is deferred to the per-scheme PRs rather than guessed at here. **Nano has nowhere in-tree to declare:** there is no Nano scheme spec and no Nano mechanism package in this repo. A binding with no in-tree spec needs a published profile a reader resolves by CAIP-2 identifier, and this draft does not solve that.

## The permit2 window, reproducible in one call

Two `eth_call` simulations of `settle(...)` against the deployed proxy, identical except for `witness.validAfter`, both using a junk 65-byte signature (`0x11` repeated) and an arbitrary owner:

- `validAfter` in the future → reverts `0xa65539fa` = `keccak256("PaymentTooEarly()")[:4]`
- `validAfter` in the past → reverts `0x8baa579f` = `keccak256("InvalidSignature()")[:4]`, Permit2's error for a signature whose `ecrecover` yields the zero address — which is what a `0x11`-repeated 65 bytes produces, since `v = 17`. It is **not** `InvalidSigner()`, which is `0x815e1d64` and a different branch of the same library; an earlier version of this draft named the wrong one of the two.

Three consequences. The error is real, deployed and **named** — an earlier version called it unnamed and that was also wrong. The window check runs **before** signature verification. And therefore the refusal reproduces from one `eth_call`: no private key, no funds, no gas, no approval, no counterparty. Both settlement entry points were probed, not one; both refuse identically.

**Probe the contract, not the prose.** `specs/schemes/exact/scheme_exact_evm.md:443` shows `require(block.timestamp >= witness.validAfter, "Too early")`, inside a `_settleInternal` declared at :437 and called at :411 and :434. That function is real — a previous "self-correction" of mine claiming it does not exist was itself wrong, and a reviewer who opened the file I cited would have found it. But the ASCII `Too early` is **not** in the deployed 2,913-byte runtime, which reverts the custom error. Same semantics, different revert encoding: an implementation MUST match the 4-byte selector, not a reason string. The contract source in this repo takes a third form again — `if (block.timestamp < validAfter) revert PaymentTooEarly();` at `contracts/evm/src/x402BasePermit2Proxy.sol:130`, in `_settle` at :117.

## The permit2 log question, asked and now answered

I was going to put this to @jywy78kgrf-create as an open question, on the strength of a sweep over the last 5,000 Base blocks that returned no logs. That window is 2 h 46 m against a contract deployed on 2026-03-11, and it is the one stretch in five months where the proxy happens to be quiet. Quiet-for-three-hours reported as no-settlements-exist is exactly the failure this thread keeps documenting, and it was mine. So here is the measurement instead of the question.

Full deployed life, keyless and re-runnable: binary-search `eth_getCode` for the deployment block (25 calls; code at 43,202,150, empty at 43,202,149), then `eth_getLogs` on the address in 10,000-block chunks to head (735 ranges, zero failed). **7,602 logs in 7,602 distinct transactions**, blocks 43,202,950 (2026-03-11T02:14:07Z) → 50,540,946 (2026-08-27T22:53:59Z). Every one has exactly one topic and `data: "0x"`. 6,672 carry `keccak256("Settled()")` = `0x97088ec3…91b6`; 930 carry `keccak256("SettledWithPermit()")` = `0xde5b89d1…f5d8` — a second settlement event on the second entry point, which reading the source alone did not surface. Negative control: the neighbouring vanity address `0x402085c248…0002` has no code and returns zero logs over the same range, so the query can come up empty.

So: this binding emits logs, and **none of them binds a settlement to an authorization** — not because a log is missing, but because every log it emits is a bare marker. Attribution lives only in the `settle()` calldata. The normative consequence, which I could not write while the question was open: *no log on the `exact`/permit2 binding binds a settlement to an authorization; a reader resolving settlements from logs alone cannot discover or attribute one here, and absence of a settlement log on this binding is NOT evidence of non-settlement — such a reader MUST NOT report `expired` or `canceled` from log absence.* Without that sentence the row reproduces the BountyBook failure with the sign flipped.

**And the method correction that goes with it.** I previously wrote that bytecode substring scanning is disproven as a method. That is too broad. Against the same 2,913-byte runtime: both emitted topic0s are present as substrings, the annex's `x402PermitTransfer` topic0 (`0xc0482a18…7dc6`) is absent, and `a65539fa`, `8baa579f` and the ASCII `Too early` are all absent while the contract provably reverts with the first two. Substring scanning discriminates 32-byte event topics — they are PUSH32 immediates — and does not discriminate 4-byte selectors, which are never stored as four contiguous bytes at rest. It has a working positive and negative control for topics, and it agrees with the log census exactly. Where logs exist, query the logs anyway.

## Worked example: a `validAfter` that is not an enforcement object

SVM `upto` is the case R2 exists for. The wire format has a `validAfter` field, and it is not a capability. `specs/schemes/upto/scheme_upto_svm.md:68`: "`validAfter` is offchain verify-time policy. Neither value is client-bound; the client signs only `open`." L893-894: "they are not client-signed terms." Verifier step 7 (L504) requires `validAfter <= now`. So the field exists, a facilitator checks it, and no third party can verify anything about it, because nothing signed commits to it and no program enforces it. A boolean capability flag would read `true` here on the strength of the field's name. Naming the contract and the field is what makes it read `absent`. It is an argument for the rule, not a row anyone is asking to declare.

## Three states credited and deferred

Each was in the previous draft's normative table. Each is dropped because it has an unresolved question, not because it is unwanted — and each question is one of you.

- **`reverted`** (@cv-scvd's `REVERTED`). §9 already ships `invalid_transaction_state` for the same fact, and on `exact`/eip3009 a reverted `transferWithAuthorization` does **not** consume the nonce — the authorization is still live and can settle. So `reverted` is terminal for the attempt and says nothing about the authorization. **Open:** is it a new state at all, or an anchor requirement attached to an existing code?
- **`mismatch`** (@cv-scvd's `INSUFFICIENT_MATCH`). The state I most want and least know how to shape. It is caller-relative: whether one chain object is `settled` or `mismatch` depends on the narrowing the caller supplied, so two conformant readers of the same settlement publish different states, and it is a status of the settlement observed, not of the authorization asked about. **Open:** whose subject is it, and does it need the narrowing carried in the anchor?
- **`indeterminate`** (@whawk46's, from his corrected #3226 table — **not** @cv-scvd's; his five values are `SETTLED`, `PENDING_FINALITY`, `NOT_FOUND`, `REVERTED`, `INSUFFICIENT_MATCH`, and the previous draft attributed this value to him twice in error). It is doing two jobs: a facilitator saying "I queried and could not resolve", and a reader saying "I rejected a peer's malformed claim". Collapsing those launders a conformance failure into an ordinary unresolved payment. **Open:** does it belong in a settlement-status vocabulary at all, or only in a reader's verdict table? @cv-scvd's `NOT_FOUND` has no home in the six either.

## What was cut, and why

- Nine states → six. The three above each have an open question; shipping them would freeze a guess.
- `basis: "scheduled"` → dropped, and this one reverses a live endorsement, so it gets more than a line. On 28 Aug 02:47 UTC I ruled the other way: `scheduled` survives by naming that it has no anchor, and I would drop it only if the group preferred. At 08:58 UTC @whawk46 endorsed that disarmed version by name, as one of three decisions he judged to "land exactly where an unforgeable protocol needs to sit". I am not going to quietly override that, so here is what changed in between, which is a finding neither of us had: **the disarmed value is not a weaker version of the state, it is a state with no situation.** `deferred_until` is parameterised on `T`, and the pre-broadcast case I kept `scheduled` for — "accepted, nothing broadcast, no ledger gate" — has no `T` to carry. So `scheduled` never covered the gap I was protecting with it. The gap is real and stays named; it needs a different construct, not a disarmed flavour of this one. `basis` keeps its place in the shape with `enforced` as its only value today. @whawk46 — this is yours to re-decide with that in hand, and if you still want it, it costs one enum value to put back.
- 20+ capability rows → three. Blast radius: the previous draft touched most of `specs/schemes/` and made every network team a required reviewer.
- SVM `upto` as a row → a worked example.
- The permit2 `canceled` anchor analysis → one line. @jywy78kgrf-create asked for that anchor on 19 Aug, I named `UnorderedNonceInvalidation` on 20 Aug and withdrew it on 23 Aug without telling you directly. It is withdrawn: no conformant `canceled` claim can be made on that binding from logs alone.
- Reader-side rules for responses that omit `status` → deleted outright. The previous draft normatively re-read `success: true` plus a non-empty `transaction` as `settled`, which would have turned every escrow deposit, hold, void and refund settle into a terminal settlement, and then forbidden the second settle from correcting it. It also contradicted the headline: you cannot say absence keeps today's semantics and legislate how absence is read.
- The ordering-evidence subsection, the conformance checklist, the security section and the census recap → the thread already carries them; they belong in the PR body.
